# ALI MCP learning-event experiment

One local stdio MCP server exposes one sending tool, `whenActive`. It captures
immediate learning evidence across any domain and appends JSONL. ALI will perform
Knowledge Graph matching, longitudinal analysis, diagnosis and adaptation later.

## Files

- `src/index.ts`: MCP registration, activation instructions, server UUID/timestamp,
  JSONL append, success/error responses, and metadata-only stderr.
- `src/learning-event.ts`: the approved seven-field strict Zod input schema.
- `scripts/smoke-test.mjs`: learning cases and format classification checks over real MCP stdio.
- `package.json`, `package-lock.json`, `tsconfig.json`: existing commands, dependencies and build settings.
- `logs/activations.jsonl`: ignored local output; old records remain untouched.
- `dist/`: ignored compiled output generated by the build.

The repository's `.codex/config.toml` still launches `dist/index.js` with Node.
MCP configuration, dependencies, and TypeScript settings are unchanged.

## Build and verify

Requires Node.js 22+. From `services/mcp-server/`:

```powershell
npm.cmd ci
npm.cmd run build
npm.cmd run test:smoke
```

The test covers a simple question, correct understanding, a possible misconception,
assisted practice correction, and privacy-minimized text. It verifies real MCP
writes, rejected inputs, old-log append compatibility, and metadata-only stderr.
Temporary logs are removed; no interactive Codex session is launched. Use
`ALI_MCP_LOG_PATH` to isolate other tests. Starting the server alone writes nothing.
Restart the MCP connection after building to refresh its schema and instructions.

## Exact input contract

All seven top-level fields are present. Missing text/topic groupings can be null;
observations and assessments can be empty arrays; recommendations can be `{}`.

| Field | Contents |
| --- | --- |
| `interaction` | `question`: complete exact original user message when available/permitted; `answer`: complete available intended answer; otherwise null |
| `interaction_type` | `mode`: conversation/practice/assessment; conversation requires `question_format: none`; practice/assessment use open_ended/multiple_choice/true_false/coding/other/none |
| `learning_intent` | What the user is trying to learn, understand, practice, or accomplish |
| `topics` | Nullable `domain` and `parent_topic`, plus a `concepts` array; suggested groupings for later ALI matching |
| `observations` | Factual statements about what the learner said, attempted, demonstrated, or corrected |
| `knowledge_assessment` | Array of `concept`, `status`, `assessment`, `evidence`, `why`, `confidence`, and optional `possible_cause` |
| `recommendations` | Optional `topics` and `practice_questions` arrays |

Classify `mode` by purpose and context, preserving relevant earlier messages:

- `conversation`: ordinary explanations, conceptual understanding checks, code
  requests, examples or help without explicit practice/assessment context.
- `practice`: explicit learning exercises intended to improve understanding
  through practice and feedback, including requests to start a practice exercise.
- `assessment`: explicit structured evaluations, tests, examinations or diagnostic
  assessments, including requests to start one.

Multiple-choice format or submitting an answer alone does not imply assessment;
asking whether an understanding is correct alone does not imply practice. Prefer
conversation without explicit practice or assessment context. Follow-ups inherit
the relevant established activity context. Smoke fixtures check these supplied
classifications survive MCP validation and persistence, not live AI decisions.

`question_format` describes an exercise, not the wording of an ordinary message.
Conversation always uses `none`, including yes/no questions, single-topic prompts,
and programming requests. Practice and assessment use the actual exercise format,
or `none` when unknown or not applicable. The schema rejects other conversation formats.

Prefer English names in `topics.domain`, `topics.parent_topic`, `topics.concepts`,
`knowledge_assessment[].concept`, `recommendations.topics[].concept`, and
`recommendations.practice_questions[].concept`. Preserve official technical terms.
Preserve the user's original language in conversational content, observations,
assessments, explanations, and evidence. This is a language preference, not a
fixed taxonomy; ALI will normalize concepts later. No name enums or translation
pipeline are introduced.

Assessment status is understanding/possible_difficulty/unknown. Confidence is
the model's confidence that the available evidence supports its assigned status
and assessment, independently judged per finding: high for strong direct evidence,
medium for partially correct or ambiguous evidence, low for weak or indirect evidence.
It is not learner confidence, overall mastery, difficulty severity, or proof of a
persistent/permanent gap. Without meaningful evidence, leave knowledge_assessment
empty. Possible causes remain hypotheses.
A question alone does not show difficulty; AI work does not prove learner knowledge.
Use empty arrays rather than inventing findings.

Keep claims such as knowing how to tune a guitar in observations as self-reports,
not objectively verified performance. If assessed, explicitly qualify them as
self-reported or unverified using the existing assessment/evidence/why/confidence
fields. Actual explanations, solutions and observable performance generally
provide stronger evidence. Confidence retains its assessment-level meaning.

Topic recommendations contain `concept`, `action` (strengthen/expand/verify), and
`why`. Practice questions contain `concept`, `question`, `purpose`, and `difficulty`
(basic/intermediate/advanced). They are suggestions, not final diagnosis decisions.
Proactively recommend 1-2 focused diagnostic practice questions when an observed
possible gap, uncertainty, or opportunity to verify understanding justifies them.
Target concepts identified in the interaction; do not invent gaps or fill the
array merely for completeness. Questions are not automatically shown to the
learner. The Diagnosis Engine and Adaptive Learning Engine choose interventions.

Objects reject extra fields. Captured text preserves whitespace and allows
1-32000 characters or null. Short explanations allow 1-2000 trimmed characters;
lists allow 30 entries, or 20 practice questions. No cross-field reference framework.

## Persistence, privacy, and limits

Each successful call stores the seven fields plus only `tool`, server-generated
UUID `invocationId`, and UTC `timestamp`; the success response includes that record.
Application/model identity is omitted because the current host supplies no reliable
identity source. The AI must not invent technical metadata.

There is no answer_status, global provenance, payload hashing, deduplication,
historical index, host metadata protocol, or profile/history lookup. Old logs are
not migrated or rewritten. Old-schema callers must refresh their MCP connection.

Activation remains broad: at most one call per potentially relevant message across
all domains, including questions, explanations, coding, problem-solving, practice,
generated work, and follow-ups. Skip unrelated small talk and privacy opt-outs.
Capture useful immediate evidence without deep diagnosis on every response.

Capture verbatim text only when authorized and available. Omit secrets, private
model reasoning, and irrelevant sensitive details; use null for withheld text.
When available and permitted, preserve the complete original user message in
`interaction.question`, including wording, uncertainty, reasoning, examples,
formatting, structure and language. Do not paraphrase, summarize, translate, or
replace it with just the main question. Use null when exact text is unavailable
or cannot be retained; do not fabricate a supposedly verbatim transcript.
Opt-outs rely on the caller following instructions. The server does not classify
consent or redact automatically. The privacy test checks withheld text, not live
agent opt-out behavior.

When calling `whenActive`, provide the most complete intended answer available in
`interaction.answer`, preserving explanations, examples, and important details.
Do not intentionally summarize or shorten the answer. Never claim it is an exact
delivered response. Use null if the answer is unavailable or not permitted.

Model-reported answer text is not necessarily a verified delivered transcript;
there is no post-response capture hook. Schema validation checks structure, not
truth. Live automatic activation has not been verified. Only protocol messages
go to stdout; stderr contains invocation IDs and generic errors, never full content.

The smoke test checks that the guidance is advertised and that multilingual
content, qualified self-reports, diagnostic recommendations, and full multiline
questions survive MCP validation and persistence. It does not prove live model
compliance, semantic correctness, or independent transcript accuracy.
